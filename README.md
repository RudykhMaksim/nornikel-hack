# Карта знаний горно-металлургической отрасли

Это MVP единой карты знаний для R&D отдела горно-металлургического института. Система строит граф, который связывает материалы, процессы, оборудование, эксперименты, публикации, экспертов и выводы. Есть поиск на естественном языке, работа с числовыми ограничениями, обнаружение противоречий и пробелов в знаниях, разграничение доступа по ролям и экспорт результатов.

Решение построено поверх реального корпуса источников (папка "Источники информации", около 1450 файлов, 4.9 гигабайта: внутренние обзоры ОИП института "Гипроникель", журналы "Горная промышленность", "Горный журнал", "Обогащение руд", "Цветные металлы", материалы конференций, статьи). Это не синтетические данные, а реально прочитанные документы.

## Архитектура

Система состоит из следующих частей.

1. Данные. Файл data/seed_data.json это курируемая онтология: около 50 сущностей и связей с реальными фактами, извлечёнными из 4 5 ключевых документов (числа, авторы, шифры ОИП, источники). Файл data/corpus_data.json это результат обработки всего корпуса: около 2100 файлов каталогизировано, около 1275 глубоко разобрано (текст плюс ключевые теги), около 5700 связей типа MENTIONS и CONTAINS. Этот файл создаётся скриптом backend/ingest/build_corpus.py.

2. Backend, папка backend/app. graph_store.py это графовое хранилище на основе networkx.MultiDiGraph, оно объединяет seed_data.json и corpus_data.json в один граф. models.py описывает типы сущностей и связей: материал, процесс, оборудование, условие, эксперимент, публикация, эксперт, организация, вывод, тема, архив. nlp.py делает простое, основанное на правилах, извлечение числовых ограничений (диапазоны, знаки не больше и не меньше), географии (Россия или международная практика) и периода дат (например "последние N лет" или явный диапазон). query_engine.py превращает запрос в нечёткое сопоставление сущностей, затем сопоставляет условия, затем обходит граф в ширину, затем фильтрует по географии и периоду, затем группирует результаты, а также находит противоречия и пробелы в знаниях. rbac.py отвечает за роли (исследователь, аналитик, руководитель проекта, администратор, внешний партнёр), скрывает внутренние сущности от внешних партнёров и ведёт аудит лог. annotations.py хранит ручные комментарии экспертов к сущностям с указанием автора и даты. versioning.py отвечает за версионирование фактов: кто, когда и почему изменил поле сущности, данные лежат в data/version_history.jsonl. export.py делает экспорт ответа в форматах Markdown, JSON LD и PDF, для кириллицы в PDF используется отдельный TTF шрифт. main.py это FastAPI приложение с эндпоинтами для поиска, получения сущности, получения графа, сравнения, поиска пробелов, дашборда, экспорта, добавления комментария к сущности, правки сущности с указанием автора и причины, и истории изменений сущности.

3. Загрузка данных, папка backend/ingest. walk_corpus.py быстро обходит весь корпус и собирает метаданные, а также список содержимого архивов, без их распаковки. extract_text.py извлекает текст из файлов форматов docx, docm, pptx, xlsx и pdf. domain_vocab.py это словарь доменных тем, которых нет в курируемой онтологии, например геомеханика, закладка, взрывные работы, флотация шлаков. build_corpus.py это главный скрипт, который запускает весь процесс загрузки.

4. Frontend. Это одностраничный интерфейс без сборки, обычные файлы html, css и js. Есть вкладки Поиск, Сравнение, Пробелы в знаниях и Дашборд. Граф отображается с помощью библиотеки vis network.

5. Дополнительно есть скрипт scripts/export_to_neo4j_cypher.py, который экспортирует граф в формат cypher для загрузки в настоящий Neo4j.

## Почему networkx, а не Neo4j

Для MVP графовое хранилище это networkx.MultiDiGraph прямо в памяти процесса FastAPI. Такой выбор не требует поднятия отдельной базы данных для проверки жюри. При этом вся модель данных, то есть типизированные узлы и связи с указанием источника, уровня достоверности и даты, полностью совместима с форматом Cypher. Файл docker compose.yml вместе со скриптом export_to_neo4j_cypher.py дают путь к настоящему Neo4j.

Путь к Cypher встроен прямо в API, а не существует только как отдельный офлайн экспорт. Модуль neo4j_store.py вместе с эндпоинтами для проверки статуса подключения и выполнения произвольного запроса на чтение (с защитой от изменяющих данные команд) дают панель в интерфейсе на вкладке Дашборд: там видно статус подключения и есть поле для запроса. Neo4j при этом необязателен: если контейнер не запущен, эндпоинт статуса честно сообщает, что база недоступна, а остальная часть приложения продолжает работать.

На практике это было проверено вживую. После запуска контейнера и импорта данных через cypher shell в базе оказалось 2196 узлов и 5704 связи, и реальные запросы на Cypher корректно возвращали данные с кириллицей. Дополнительно граф был временно досеян синтетическими данными до 1 002 196 узлов и 955 704 связей, то есть ровно до объёма, указанного в нефункциональных требованиях технического задания. На этом масштабе обход графа в четыре шага от узла "сульфаты", доходящий почти до всего графа, занял 2.5 секунды, что укладывается в требуемые 3 5 секунд. Типовой точечный запрос с двумя шагами обхода занял около 1.8 секунды. После проверки синтетические данные были удалены, и в базе снова остался только реальный граф.

## Как запустить

1. Установить зависимости из файла requirements.txt.
2. Запустить сервер командой uvicorn backend.app.main:app, порт 8010, с автоматической перезагрузкой.
3. Открыть в браузере адрес 127.0.0.1:8010.

Для запуска тестов нужно установить pytest и httpx, затем выполнить команду python m pytest backend/tests с флагом v.

## Как пересобрать граф из реального корпуса

Данные уже собраны и лежат в файле data/corpus_data.json. Сами исходные файлы, папка "Источники информации" объёмом 4.9 гигабайта, не входят в репозиторий, там только производные файлы в формате json.

Чтобы пересобрать граф заново или указать другой путь к исходным файлам, нужно запустить модуль backend.ingest.build_corpus с указанием пути к папке источников, а также ограничений на число файлов для глубокого разбора и на время выполнения.

Используется двухслойный подход.

1. Быстрый каталог. Собираются метаданные вообще всех файлов: путь, папка категория, формат, размер. Для архивов формата zip собирается список содержимого без распаковки. Это дало около 2090 записей за несколько секунд.

2. Глубокое извлечение текста и ключевых тегов. Полностью разбираются все дешёвые форматы: docx, docm, pptx, xlsx, около 123 файла. Также разбираются файлы pdf по приоритету: сначала те, что по имени совпадают со словарём доменных тем, затем остальные по возрастанию размера. Есть ограничение по числу файлов и по времени выполнения. В последнем прогоне было разобрано 1275 из 1528 пригодных для разбора файлов примерно за 100 секунд, найдено около 5700 связей типа MENTIONS.

По форматам. Файлы docx, docm, pptx и xlsx разбираются полностью без проблем с кириллицей. Файлы pdf разбираются библиотекой PyMuPDF, а не утилитой pdftotext: было обнаружено и подтверждено, что сборка xpdf, которая идёт вместе с Git for Windows, теряет всю кириллицу на реальных файлах корпуса, потому что во встроенных шрифтах нет нужной таблицы соответствия символов. Файлы старого бинарного формата doc и xls, а также архивы rar и многотомные архивы, не разбираются по содержимому, потому что в окружении нет нужных инструментов для распаковки. Для них собираются только метаданные, это видно в дашборде в отдельном показателе.

## Провенанс данных

Часть курируемой онтологии построена на прочтении пяти ключевых внутренних документов из корпуса, а не на выдумке. Ниже соответствие между сценариями из технического задания и реальными источниками.

1. Методы обессоливания воды. Источник: документ "Методы очистки шахтных вод" из папки Обзоры, шифр ОИП 02 2025. В нём описаны реальные методы: процесс SAVMIN, процесс с высокоплотным шламом, обратный осмос и нанофильтрация, ионный обмен, биологическое восстановление сульфата. Есть реальные цифры: на заводе Stillfontein в Южно Африканской Республике процесс SAVMIN снизил концентрацию сульфата с 800 до менее 200 миллиграмм на литр, а традиционное известкование ограничено значением 1500 2500 миллиграмм на литр из за растворимости гипса.

2. Циркуляция католита при электроэкстракции никеля. Источник: документ "Обзор технических решений в области электролитического производства никеля и меди" из папки Обзоры, шифр ОИП 03 2025. В нём описана технология параллельных потоков METTOP BRX на заводе Brixlegg в Австрии с плотностью тока 400 420 ампер на квадратный метр, что на 50 процентов выше обычного значения, а также хлоридный электролит на заводах Nikkelverk в Норвегии и Niihama в Японии.

3. Распределение золота, серебра и металлов платиновой группы между штейном и шлаком. Источник: документ "Распределение Au, Ag и МПГ между медным и никелевым штейном и шлаком" из папки Обзоры, шифр ОИП 06 2018. В нём указаны реальные исследователи: G.Roghani, M.Henao, специалисты Университета Аалто, J.M.Font из компании Codelco, а также Avarmaa и Taskinen, и реальные условия опытов.

4. Закачка шахтных вод в глубокие горизонты. По этой теме не найдено ни одного документа во всём каталогизированном корпусе, это было проверено полнотекстовым поиском по ключевым словам. Этот пробел в знаниях представлен как честный, а не придуманный.

5. Пробел по кучному выщелачиванию никелевой руды в холодном климате. Источник: документ "ТИ 5 2017. Кучное выщелачивание в условиях холодного климата" от ООО "Институт Гипроникель", 2017 год. Этот документ целиком посвящён медной руде. Для никелевой руды в холодном климате подтверждающих экспериментов действительно нет, это ровно тот пробел, который описан в самом техническом задании.

6. Патенты, всего два реальных патента. Оба процитированы внутри документа "Методы очистки шахтных вод": "Способ очистки сточных вод от ионов тяжёлых металлов" с использованием известкового молока и принудительной подачи углекислого газа, и "Способ очистки шахтных сточных вод от сульфатов" с использованием вымораживания, известкования и осаждения сульфата бария. В графе это отдельный тип сущности "Патент", а не просто публикация.

7. Термин ПВП, то есть печь взвешенной плавки. Источники: документы "ОИП 05 2022, тенденции" и "Обеднение шлаков" из папки Обзоры. В них указаны реальные цифры компании Outotec: от 25 до 35 тысяч тонн никеля в год в файнштейне, от 15 до 25 процентов меди в шлаке печи взвешенной плавки. Это тот самый канонический пример синонимов из текста самого технического задания: "ПВП", "печь взвешенной плавки" и английское "fluidized bed furnace".

Реальные авторы и организация, которые встречаются в графе: Р.А. Кузнецов, начальник ОИП, А.К. Евграфова, главный специалист, Л.Б. Цымбулов и С.М. Козырев, в разные годы директора Департамента по исследованиям и разработкам, и организация ООО "Институт Гипроникель". Эти данные предоставлены организаторами специально для соревнования, поэтому публикация в открытом репозитории не создаёт проблем с конфиденциальностью.

## Соответствие функциональным требованиям технического задания

1. Импорт разнородных форматов: docx, docm, pptx, xlsx, pdf, zip.
2. Извлечение сущностей, связей и числовых ограничений с помощью простых и прозрачных для проверки правил, вместо непрозрачной модели.
3. Поддержка русского и английского языков: тот же самый механизм разбора числовых ограничений, географии и периодов дат работает на английском не хуже, чем на русском, и все четыре примера запросов из технического задания дают одинаковый результат на английской формулировке.
4. Граф знаний с типизацией сущностей: у каждой сущности есть уровень достоверности, дата последнего обновления, уровень чувствительности и ссылка на источник.
5. Версионирование фактов, реализовано двумя независимыми способами. Первый способ ручной: правка сущности с обязательным указанием автора и причины, изменения пишутся в отдельный файл истории и доступны через отдельный запрос истории изменений. Второй способ автоматический: при каждом повторном запуске сборки корпуса система сама сравнивает новый результат с предыдущим, определяет новые документы и новые связи, и записывает сводку изменений без участия человека. Это видно на вкладке Дашборд.
6. Семантический поиск с фильтрами по материалу, процессу, географии, году и числовому диапазону.
7. Хранение с поддержкой Cypher: граф в памяти процесса плюс живой путь в настоящий Neo4j прямо внутри API, а не только офлайн экспорт.
8. Визуализация графа и подсветка пробелов в знаниях на вкладках Поиск и Пробелы в знаниях.
9. Генерация структурированных ответов с выделением консенсуса и разногласий.
10. Сопоставление синонимов и терминов реально подключено к поиску, а не существует просто как справочник. Например запрос на "ПВП", на "печь взвешенной плавки" и на "fluidized bed furnace" уверенно приводит к одной и той же сущности.
11. Патенты выделены как отдельный тип сущности, а не безликая публикация.
12. Фильтр по уровню достоверности результатов.
13. Отчёт "только в России" и "только за рубежом" для каждой курируемой технологии или материала.
14. Разграничение доступа по ролям и ведение аудит лога.
15. Экспорт результатов в форматах Markdown, JSON LD и PDF.
16. Ручная корректировка графа экспертами через добавление комментариев и через правку полей сущности.
17. Дашборд с покрытием знаний по типам, по географии и по уровню достоверности, а также с метриками загрузки данных.
18. Производительность на масштабе около одного миллиона сущностей проверена вживую и укладывается в требуемые 3 5 секунд.

## Ограничения и что делать дальше

1. Механизм извлечения данных это регулярные выражения и словарь синонимов, а не обученная модель машинного обучения. Такой результат детерминирован и его можно объяснить построчно, но для промышленного использования стоит дополнить его эмбеддингами для семантического поиска и полноценной лемматизацией, сейчас используется только грубое усечение слова. Морфология среднего рода на коротких словах иногда не распознаётся. Ранжирование результатов поиска эвристическое, по весу типа связи, а не полноценное обученное ранжирование.

2. Глубокий разбор файлов pdf ограничен по числу файлов, по числу страниц и по размеру файла. Из 1528 пригодных для разбора файлов за один прогон разобрано 1275, остальные файлы, а также все файлы форматов doc, xls и rar видны в каталоге по метаданным, но не проиндексированы по содержимому. Повторный запуск сборки корпуса с большим бюджетом времени дособирает оставшееся.

3. Разграничение доступа по ролям сейчас устроено так, что роль передаётся клиентом напрямую, без единой системы входа. Это подходит для демонстрации, но не для промышленной эксплуатации.

4. Поддержка английского языка ограничена: это по прежнему набор регулярных выражений и словарь ключевых слов и оборотов, а не полноценная модель распознавания именованных сущностей с настоящей лемматизацией.

5. Интеграции с уведомлениями о появлении новых публикаций нет, для этого потребовался бы внешний сервис электронной почты или мессенджера.

6. Географическая привязка около двух тысяч документов реального корпуса определяется эвристикой: по названию папки, либо по соотношению кириллицы и латиницы в имени файла и в начале текста, а не человеком и не по метаданным документа. Это приближение, а не точная разметка.

7. Автотесты для версионирования на самом деле вызывают правку сущности и меняют рабочий файл курируемой онтологии, откатывая изменения после каждого теста. В промышленной среде тесты должны бы работать с отдельной копией файла, а не с рабочим файлом.

8. Реальный корпус объёмом 4.9 гигабайта не входит в репозиторий и в архив поставки, туда входят только производные файлы в формате json и код.
