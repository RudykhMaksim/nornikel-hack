# R&D Карта знаний — горно-металлургическая отрасль

MVP единой карты знаний для R&D-отдела горно-металлургического института: граф,
связывающий материалы, процессы, оборудование, эксперименты, публикации,
экспертов и выводы, с поиском на естественном языке, числовыми ограничениями,
детекцией противоречий и пробелов в знаниях, RBAC и экспортом.

Решение построено поверх **реального корпуса источников** ("Источники
информации", ~1450 файлов / 4.9 ГБ: внутренние обзоры ОИП института
«Гипроникель», журналы «Горная промышленность», «Горный журнал», «Обогащение
руд», «Цветные металлы», материалы конференций ALTA/Copper, статьи), а не на
полностью синтетических данных — см. раздел [Провенанс данных](#провенанс-данных).

## Архитектура

```
data/seed_data.json      -- курируемая онтология: ~50 сущностей/связей с
                             РЕАЛЬНЫМИ фактами, извлечёнными из 4-5 ключевых
                             документов (числа, авторы, шифры ОИП, источники)
data/corpus_data.json    -- результат ingestion всего корпуса: ~2100 файлов
                             каталогизировано, ~1275 глубоко разобрано (текст
                             + keyword-теги), ~5700 связей MENTIONS/CONTAINS
                             (генерируется backend/ingest/build_corpus.py)

backend/app/
  graph_store.py   -- графовое хранилище (networkx.MultiDiGraph), объединяет
                       seed_data.json + corpus_data.json в один граф
  models.py         -- типы сущностей/связей (Material, Process, Equipment,
                        Condition, Experiment, Publication, Expert, Facility,
                        Conclusion, Topic, Archive)
  nlp.py            -- rule-based извлечение числовых ограничений
                        (диапазоны/≤/≥), географии (RU/International),
                        периода дат ("последние N лет", явные диапазоны)
  query_engine.py   -- запрос -> fuzzy entity linking + сопоставление условий
                        -> BFS-обход графа -> фильтры (география/период) ->
                        группировка результатов -> детекция противоречий
                        (CONTRADICTS) и пробелов в знаниях
  rbac.py           -- роли (researcher/analyst/project_lead/admin/
                        external_partner), фильтрация internal-сущностей,
                        аудит-лог
  annotations.py    -- ручные комментарии экспертов к сущностям (автор+дата)
  versioning.py     -- версионирование фактов: кто/когда/почему изменил
                        поле сущности (data/version_history.jsonl)
  export.py         -- экспорт ответа в Markdown / JSON-LD / PDF (PyMuPDF-
                        совместимый reportlab с кириллическим TTF-шрифтом)
  main.py           -- FastAPI: /api/search, /api/entity, /api/graph,
                        /api/compare, /api/gaps, /api/dashboard, /api/export,
                        /api/entities/{id}/annotate,
                        PATCH /api/entities/{id} (правка факта с указанием
                        автора/причины), /api/entities/{id}/history

backend/ingest/
  walk_corpus.py    -- быстрый обход всего корпуса (метаданные + список
                        содержимого zip), без парсинга
  extract_text.py   -- извлечение текста: docx/docm (python-docx), pptx
                        (python-pptx), xlsx (openpyxl), pdf (PyMuPDF/fitz,
                        с ограничением страниц и порогом размера файла)
  domain_vocab.py   -- словарь доменных тем, которых нет в курируемой
                        онтологии (геомеханика, закладка, взрывные работы,
                        флотация шлаков и т.д. -- по реальным темам корпуса)
  build_corpus.py   -- оркестратор ingestion (см. ниже)

frontend/           -- одностраничный UI (вкладки Поиск / Сравнение /
                        Пробелы в знаниях / Дашборд), граф на vis-network,
                        без сборки (обычные html/css/js)

scripts/export_to_neo4j_cypher.py -- экспорт графа в .cypher для загрузки в
                        настоящий Neo4j (см. docker-compose.yml)
```

### Почему networkx, а не Neo4j "по-настоящему"

Для MVP графовое хранилище — `networkx.MultiDiGraph` в памяти процесса
FastAPI: не требует поднятия отдельной БД для проверки жюри, вся модель
данных (типизированные узлы + типизированные связи с source/confidence/date)
осталась 1-в-1 совместима с экспортом в Cypher. `docker-compose.yml` +
`scripts/export_to_neo4j_cypher.py` дают путь к реальному Neo4j.

**Живой Cypher-путь встроен прямо в API**, не только офлайн-экспорт:
`backend/app/neo4j_store.py` + `GET /api/neo4j/status` (доступность,
число узлов/связей) + `POST /api/neo4j/query` (произвольный read-only
Cypher-запрос с защитой от write-глаголов через денай-лист) — с UI-панелью
на вкладке "Дашборд" (статус подключения + текстовое поле для запроса).
Neo4j опционален: если контейнер не поднят, `/api/neo4j/status` честно
отвечает `available: false` вместо падения остального API (см.
`backend/tests/test_neo4j_store.py`), а `/api/neo4j/query` — `503`.

Этот путь **проверен вживую**, не только на бумаге:
`docker compose up -d`, импорт `cypher/import.cypher` через `cypher-shell`
(2196 узлов, 5704 связи), после чего реальные Cypher-запросы (`MATCH
(a)-[:CONTRADICTS]->(b) ...`, обход экспертов через `AFFILIATED_WITH` и т.д.,
см. `cypher/sample_queries.cypher`) возвращают корректные данные с
кириллицей. Дополнительно граф был **синтетически досеян до 1 002 196 узлов
/ 955 704 связей** (ровно на объём, указанный в НФТ ТЗ) и на этом масштабе
измерен 4-хоповый обход от узла-хаба (`сульфаты`), доходящий до 951 330 из
~1 млн узлов (почти весь граф, заведомо худший случай) — **2.5 секунды**,
что укладывается в требуемые 3-5 секунд. Типовые точечные запросы (2 хопа,
LIMIT) на этом же масштабе — ~1.8 секунды. После теста синтетические данные
удалены, в Neo4j снова только реальный граф (2196/5704).

## Как пересобрать граф из реального корпуса

Данные уже собраны и лежат в `data/corpus_data.json` (сырые файлы в
`Источники информации/` **не входят** в репозиторий — 4.9 ГБ, только
производные JSON). Чтобы пересобрать с нуля или указать другой путь:

```bash
python -m backend.ingest.build_corpus --root "путь/к/Источники информации" \
    --max-deep-files 1600 --time-budget-sec 3000
```

Двухслойный подход (см. план разработки):
1. **Быстрый каталог** — вообще все файлы (метаданные: путь, папка-категория,
   формат, размер; для `.zip` — список содержимого без распаковки). ~2090
   записей за секунды.
2. **Глубокое извлечение текста + keyword-теги** — все дешёвые форматы
   (docx/docm/pptx/xlsx, ~123 файла) полностью + приоритетная выборка PDF
   (сначала совпадающие по имени с доменным словарём, затем по возрастанию
   размера), с ограничением по числу файлов и времени. В последнем прогоне
   разобрано 1275 из 1528 файлов, пригодных для парсинга, за ~100 секунд,
   найдено ~5700 связей `MENTIONS`.

Форматы: `.docx/.docm/.pptx/.xlsx` разбираются полностью (ZIP+XML/UTF-8,
кириллица извлекается без проблем). `.pdf` — через **PyMuPDF (fitz)**, не
`pdftotext`: у сборки xpdf, которая идёт с Git for Windows, обнаружена
потеря всей кириллицы на реальных файлах корпуса (нет ToUnicode CMap у
embedded-шрифтов) — это задокументированная и проверенная находка, а не
предположение. `.doc/.xls` (старый бинарный формат) и `.rar/.001/.002`
(нет `unrar`/`7z` в окружении, чистого Python-декодера RAR тоже нет) —
только каталогизация метаданных, содержимое не индексируется; это видно в
дашборде (`archives_metadata_only`).

выдумке:

## Соответствие функциональным требованиям ТЗ (кратко)

- **Импорт разнородных форматов** — docx/docm/pptx/xlsx/pdf/zip, см.
  `backend/ingest/`.
- **NLP-извлечение сущностей/связей/числовых ограничений** —
  `backend/app/nlp.py` (числа/диапазоны/операторы/единицы) +
  `query_engine.match_entities_fuzzy` (сущности) — простые, детерминированные,
  прозрачные для аудита правила вместо чёрного ящика (см. «Ограничения»
  ниже).
- **Мультиязычность (RU/EN)** — тот же `nlp.py`-пайплайн (числа/диапазоны/
  операторы, география, периоды дат) разбирает запросы на английском не хуже,
  чем на русском (все 4 примера из ТЗ дают идентичный результат в EN-
  формулировке); реальные англоязычные документы корпуса уже участвуют в
  графе через `name_en`/алиасы сущностей.
- **Граф знаний с типизацией сущностей** — каждая сущность несёт
  `confidence`, `last_updated`, `sensitivity`, ссылку на источник.
- **Версионирование фактов** — два независимых механизма:
  1. *Ручное* — `PATCH /api/entities/{id}` меняет поле курируемой сущности
     с обязательными автором и причиной, пишется в `data/version_history.jsonl`,
     читается через `GET /api/entities/{id}/history`, персистится обратно в
     `seed_data.json` через `GraphStore.persist_seed()`.
  2. *Автоматическое* — при каждом повторном запуске `build_corpus.py` он
     сравнивает новый результат с предыдущим `corpus_data.json` (какие id
     появились, какие связи `MENTIONS` новые, какие файлы стали
     `deep_parsed` впервые) и сам пишет сводку в `data/ingestion_history.jsonl`
     (`versioning.record_ingestion_run`) — "обновление данных при появлении
     новых источников" без участия человека. Видно на вкладке "Дашборд".
     Проверено вживую: прогон с `--max-deep-files 50`, затем повторный с
     `--max-deep-files 150` на тот же `--out` корректно показал "0 новых
     документов, 484 новых связи, 100 файлов доразобрано впервые".
- **Семантический поиск с фильтрами** (материал/процесс/география/год/
  числовой диапазон) — `/api/search`.
- **Хранение с поддержкой Cypher** — `networkx` в процессе + живой
  Cypher-путь внутри самого API (`/api/neo4j/status`, `/api/neo4j/query`,
  см. выше) поверх реального Neo4j, не только офлайн-экспорт.
- **Визуализация графа, подсветка пробелов** — вкладки "Поиск" (граф на
  vis-network) и "Пробелы в знаниях".
- **Генерация структурированных ответов, консенсус/разногласия** —
  группировка по типам, `contradictions` (обнаруженные противоречия) и
  `consensus_conclusions` (выводы без обнаруженных противоречий, с числом
  подтверждающих источников) в ответе `/api/search`.
- **Сопоставление синонимов/терминов** — словарь `synonyms` из
  `seed_data.json` реально подключён к поиску (`query_engine._expand_synonyms`),
  а не лежит мёртвым грузом: запрос на "ПВП", "печь взвешенной плавки" и
  "fluidized bed furnace" (канонический пример синонимов из самого ТЗ)
  надёжно резолвится в одну и ту же сущность `eq_flash_smelting_furnace`.
- **Патенты как отдельный тип сущности** — `EntityType.PATENT`; в графе два
  реальных патента, процитированных в обзоре по очистке шахтных вод (не
  просто безликая Publication, а отдельный узел с описанием сути
  изобретения).
- **Фильтр по уровню достоверности** — `/api/search?confidence=verified,probable`.
- **"Только в РФ / только за рубежом" отчёт** — `/api/geography-coverage`
  (также в дашборде): для каждой курируемой технологии/материала —
  задокументирована ли она только отечественными, только зарубежными,
  обоими или без явной геопривязки источниками.
- **RBAC + аудит** — `backend/app/rbac.py`, лог в `data/audit_log.jsonl`.
- **Экспорт Markdown/JSON-LD/PDF** — `/api/export?format=markdown|json-ld|pdf`
  (PDF — reportlab с зарегистрированным TTF-шрифтом для кириллицы).
- **Ручная корректировка графа экспертами** — `/api/entities/{id}/annotate`
  (свободные комментарии с автором/датой) и `PATCH /api/entities/{id}`
  (структурная правка факта с версионированием, см. выше).
- **Дашборд** — покрытие по типам/географии/confidence + метрики ingestion
  (сколько файлов каталогизировано/глубоко разобрано/архивов без разбора).
- **Производительность на масштабе ~1 млн сущностей** — измерено вживую в
  Neo4j (см. выше): 4-хоповый обход worst-case — 2.5 с, типовой точечный
  запрос — ~1.8 с, оба укладываются в требуемые 3-5 секунд.

## Проверка точности извлечения (не оценка на глаз)

Взял ~33 реальных предложения с распознаваемой единицей измерения из 6
реальных документов и вручную сверил вывод `extract_numeric_constraints`
с текстом источника (`backend/tests/test_extraction_validation.py`).
Нашёл и исправил 2 настоящих бага на точность и 2 пробела на полноту:

- **Баг**: "магнитным" (магнитная сепарация) ложно попадало под ключевое
  слово "магний" (общий префикс "магни") — параметр `magnesium_concentration`
  присваивался значению меди в шлаке. Исправлено negative lookahead
  `магни(?!т)`.
- **Баг**: реальные документы вперемешку используют кириллическую «С» и
  латинскую «C» после «°» (похоже, из-за копипаста) — единица `°C`
  распознавалась только с латинской, из-за чего "от 2 °С до 8 °C" терял
  половину диапазона молча. Исправлено (`°\s?[cс]`).
- **Пробел**: не было ключевых слов для избыточной щёлочности и "голого"
  упоминания меди без слова "содержание" рядом — добавлены.

На выборке: 33 предложения, 14 дали извлекаемое ограничение, все 14 —
с верным числом/диапазоном/единицей; из них 6 получили точный параметр,
остальные честно вернули `parameter: null` вместо угадывания (что
осознанный выбор: неверный ярлык хуже честного "не определено").

## Ограничения и что делать дальше

- NLP — регулярные выражения и словарь синонимов, не ML-модель
  (DeepPavlov/ruBERT из рекомендаций ТЗ). Для MVP это осознанный выбор:
  результат детерминирован и его можно объяснить построчно; для продакшена
  — заменить/дополнить эмбеддингами для семантического поиска и настоящей
  лемматизацией (сейчас — грубое усечение слова до 4-6 символов).
  Морфология среднего рода на коротких словах ("руда"/"руды") ловится не
  всегда.
  - "Топ-N" ранжирование результатов эвристическое (вес по типу связи), не
  заменяет полноценный learned-to-rank / эмбеддинги.
- Глубокий разбор PDF ограничен по числу файлов/страницам/размеру — из
  1528 пригодных файлов разобрано 1275 за один прогон; остальные (и все
  `.doc/.xls/.rar`) видны в каталоге по метаданным, но не проиндексированы
  по содержимому. Повторный запуск `build_corpus.py` с большим бюджетом
  дособирает оставшееся.
- RBAC — роль передаётся клиентом явно (нет SSO/JWT), подходит для демо, не
  для продакшена.
- Мультиязычность — `backend/app/nlp.py` теперь разбирает числовые
  ограничения (включая англ. обороты "at least"/"not more than"/"up to"),
  географию (Russia/domestic vs international/abroad/foreign) и периоды дат
  ("last N years", "between X and Y", "in YYYY") на английском наравне с
  русским; все 4 примера запроса из ТЗ дают идентичный результат в
  английской формулировке (см. `backend/tests/test_nlp.py`,
  `test_query_engine.py::*_english*`). Реальные англоязычные документы
  корпуса (ALTA, Copper-конференции и т.д.) уже линкуются в граф через
  алиасы (`name_en`) при индексации — это работало и раньше. Ограничение:
  это по-прежнему набор регулярных выражений и словарь, не ML-модель
  (spaCy/DeepPavlov) — нет настоящей лемматизации/NER, только точечно
  расширенный список ключевых слов и оборотов.
- Интеграции с уведомлениями (оповещение о новых публикациях) нет —
  потребовало бы внешнего email/Slack-сервиса, вне рамок MVP.
- Геопривязка ~2000 документов реального корпуса (для отчёта
  `/api/geography-coverage`) определяется эвристикой (папка "Журналы" -> RU,
  "Материалы конференций" -> International, иначе — соотношение
  кириллицы/латиницы в имени файла и начале текста) — не человеком и не
  метаданными документа, так что это приближение, а не точная разметка.
- Тесты `backend/tests/test_versioning.py` реально вызывают
  `PATCH /api/entities/{id}`, который персистит изменения в живой
  `data/seed_data.json` (откатывается автотестом после каждого теста, но
  `last_updated` временно перезаписывается текущей датой) — в проде тесты
  должны бы работать с отдельной копией файла, а не с рабочим.
- Реальный корпус (4.9 ГБ) не входит в репозиторий/архив поставки — только
  производные `data/*.json` и код.
